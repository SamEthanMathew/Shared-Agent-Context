The model is not the authorisation layer.

Identity, membership, and scope are resolved by the server before any context is assembled. An agent cannot receive memory its caller isn't entitled to, because that memory never enters the response.

Enforced today

What Osmos actually does

Everything on this page is implemented and running. Where something is designed but not yet enforced, it is in the next section instead.

Verified identity An OAuth 2.1 authorization server runs inside the service — authorization code with PKCE, dynamic client registration, and Client ID Metadata Documents. Tokens are verified on both the MCP and REST surfaces by the same provider. People sign in with Google, GitHub, or an email address and password.
Per-client connections Each connected assistant is a distinct, listed connection carrying its own identity. Connections are revocable individually, without disturbing the others, and the next call from a revoked one fails.
Private and shared scopes Private memory belongs to the person who wrote it; shared memory belongs to the context. The distinction is enforced in storage and in retrieval, not by asking a model to keep a secret.
Filtering before assembly Permission filtering happens in SQL, before context is compiled. This is the architectural difference that matters: unauthorised memory is never selected, rather than selected and then removed.
Sharing is a human action There is no tool an assistant can call to grant anyone access. Every grant is made by a person, in the app, and is recorded. An agent cannot be talked into widening access it does not control.
Re-sharing stays with people A share link can grant view or edit, never manage — and neither can organisation access. Manage carries the right to re-share, and a link or a group membership that could pass that on would propagate access no human chose.
Groups grant nothing by default Creating an organisation, adding people to it, and moving a context into it all grant nothing on their own; access begins only when someone sets that control. An individual invitation outranks it, so removing a person from the group revokes only what the group gave them.
Address ownership is proven An unverified account cannot create contexts or accept shares, and an unverified address is treated as no account at all — otherwise anyone could register someone else's address and quietly collect the contexts shared to it. Federated sign-in that cannot prove the address is refused rather than linked.
Provenance Durable knowledge carries the evidence it came from, its author, its agent, its type, and its time. A claim inferred by an agent is distinguishable from a decision made by a person.
Versions and supersession Knowledge can explicitly supersede earlier knowledge. History is retained, so you can see what the project used to believe and when that changed. Anything wrong can be retracted, and agents stop receiving it.
A record of what each agent saw Every sync is recorded: the task, the revision, what was included, how much was withheld and why, and the token estimate against the requested budget. Withheld items are counted, never named. The record belongs to the person whose agent made the call — not even a context's owner can read someone else's, because it enumerates their private memory.
Access history Who shared what with whom, every access change, and every archive or restore are kept for as long as the context exists. "When did this become visible to them" is a question asked months later, so the answer is not something retention removes.
Archiving keeps the memory Archiving a context removes it from every listing and stops agents seeing it immediately, but deletes nothing. Restoring it brings everything back at the same revision.
Monotonic revisions Each context carries a revision that only moves forward, so a client can tell whether anything changed since it last synced.
Retention

How long things are kept

Retention never touches the product's actual content. It expires the by-products that would otherwise become an asset of their own.

Memory — indefinitely

Shared and private memory is the project brain. It is kept until you retract it or delete the context.

Access history — indefinitely

Small, append-only, and the record you need to answer a question about who could see what, and when.

Sync records — 90 days

Each one lists the memories fed to one person's agent, including their private ones. Long enough to answer "what did it know", short enough not to accumulate a history of everything each assistant ever saw.

Limits

What it does not do yet

Stated plainly, because a product about inspectable knowledge cannot be vague about its own.

Sensitivity ceilings are not enforced

Every memory carries a sensitivity label, and writes marked secret are refused. But per-grant sensitivity ceilings — capping what a specific client may ever receive — are designed and not yet implemented.

Local mode is unauthenticated

The default dev mode identifies callers from an actor email supplied by the client. It is spoofable by design and exists for local development. Public deployments must set SAC_AUTH_MODE=auth.

No compliance certifications

Osmos holds no SOC 2, ISO 27001, or HIPAA attestation, and this page will not claim otherwise. You run the service yourself, on infrastructure you control and are responsible for.

Retrieval is lexical

Ranking combines lexical match, type, importance, and recency. There is no embedding model yet. The trade is inspectability and determinism over semantic recall.

The two rules underneath

Connecting a client is not consent to share everything

Authorising an agent grants it an identity, not the project's entire contents. What it can read is a function of who its caller is and what scope the knowledge lives in — evaluated per request.

Retrieved context is data, not instructions

Knowledge returned by Osmos is evidence for the agent to reason over. It is never treated as higher-priority instruction, which is what keeps a poisoned memory from becoming a command.

Inspect it yourself.
